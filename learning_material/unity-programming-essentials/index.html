Learning outcomes

Build an interaction whose visible result can be traced to components and code.

The finished living room has one controllable player, a following camera, and a readable route of collectibles. Each pickup rotates, detects only the Player, disappears, and creates visual feedback.

  • Explain why a C# script becomes a component on a GameObject.
  • Configure the Input System and a Rigidbody-based movement loop.
  • Distinguish Start, Update, and FixedUpdate.
  • Expose editable fields and test them without losing final values.
  • Connect trigger overlap to tag filtering, VFX, and destruction.
  • Diagnose a failure from its visible symptom and likely responsibility.
Opening demonstration Run the completed scene once without opening any code. Move and turn the player, collect three objects, then stop. Ask students to identify the GameObject, component, field, or event responsible for movement, camera following, rotation, overlap detection, object removal, and the particle effect.

01 · PROJECT → PLAYER → COMPONENTS

Set up the scene before diagnosing code

Programming does not replace the component model you already know. A script supplies behavior, but the scene still depends on the right GameObject, Rigidbody, Collider, camera relationship, and project input setting.

02 · INPUT → RIGIDBODY MOTION

Create a movement script and attach it as a component

A MonoBehaviour script becomes an attachable component. The PlayerController below reads the new Input System, caches the Player’s Rigidbody once, and moves that Rigidbody during Unity’s fixed physics update.

  1. Open _Unity Essentials → Scripts. Right-click empty space and select Create → MonoBehaviour Script.
  2. Name the new file PlayerController immediately. The file name and class name must match exactly.
  3. Drag PlayerController from the Project window onto Player in the Scene view.
  4. Select Player in the Hierarchy and verify Player Controller (Script) at the bottom of the Inspector.
  5. Double-click the script to open the configured script editor, replace the template with the supplied code, and save the file.
  6. Return to the Unity Editor, wait for compilation to finish, enter Play mode, and test both WASD and the arrow keys.
Code regionResponsibilityVisible or testable result
usingMakes UnityEngine and Input System types available.Keyboard, Rigidbody, and Vector3 resolve.
Public fieldsStore speed values and serialize them for the Inspector.Speed and Rotation Speed appear on Player.
StartGets the Rigidbody component once and warns if it is absent.The movement code has a physics body to control.
FixedUpdateReads held keys and performs fixed-step physics motion.Movement remains proportional to units or degrees per second.
MovePositionMoves along the Player’s forward direction.W/Up moves forward; S/Down reverses.
MoveRotationRotates around the Y-axis.A/Left and D/Right turn the Player.
Movement proof Run a four-part test: forward, reverse, turn while moving forward, then turn while reversing. Record which visible behavior would fail if the Input System, Rigidbody, or saved script were missing.
03 · HIERARCHY + CONTROLLED TUNING

Make the camera follow, then tune one field at a time

Parenting transfers motion through the Transform hierarchy. When Main Camera is a child of Player, its position and rotation are local to Player, so the camera follows without a second movement script.

  1. Drag Main Camera onto Player in the Hierarchy. Confirm that it becomes indented beneath Player.
  2. Open the Main Camera Transform component’s More (⋮) menu and select Reset.
  3. Move the camera slightly above and behind Player. Use the camera Preview panel to frame the character.
  4. Enter Play mode, select Player, and change only Speed. Test the same route twice.
  5. Restore Speed, change only Rotation Speed, and repeat the turn test.
  6. Write down the preferred values, exit Play mode, apply those values again outside Play mode, and save the scene.
PLAY MODE EXPERIMENT

Immediate feedback is useful for comparison, but Inspector changes revert when Play mode ends.

EDIT MODE COMMIT

Reapply the chosen values after exiting Play mode, then save the scene so the configuration persists.

Temporary state The blue Play control means you are testing runtime state. Do not assume a tuned value is saved. If movement stops after clicking the Inspector, click the Game view once to return keyboard focus.

04 · MONOBEHAVIOUR + UPDATE

Write a small component that rotates a collectible

The Collectible script is the first behavior written line by line. Its structure separates the component definition from event functions and editable data; Update is the event used for continuous per-frame visual motion.

  1. From _Unity Essentials → Prefabs → Collectibles, place one collectible directly in front of Player.
  2. Create a Collectible MonoBehaviour script in the Scripts folder and drag it into the collectible’s Inspector.
  3. Open the script and locate using UnityEngine;, the class declaration, Start, and Update.
  4. Switch the Scene view handle orientation to Local. Scrub Transform → Rotation → Y to preview the intended axis.
  5. Inside Update, add transform.Rotate(0, 1, 0);, save, and test the fast rotation.
  6. Change the Y value to 0.5f, save, and compare the slower rotation.
  7. Declare public float rotationSpeed; above the event functions, then replace the literal with rotationSpeed.
  8. Save, return to Unity, set Rotation Speed in the Inspector, and test again.
StructureMeaning in this componentCommon confusion
using UnityEngine;Makes Unity types and APIs available.It does not attach the script to a GameObject.
class CollectibleNames the custom component type.The class name must match Collectible.cs.
: MonoBehaviourMakes the class an attachable Unity component with event functions.A GameObject itself does not need a MonoBehaviour.
StartRuns once before the first Update while enabled.It is not the place for continuous rotation.
UpdateRuns once per rendered frame while enabled.Its frequency varies with frame rate.
Public float fieldStores a decimal value and appears as Rotation Speed in the Inspector.0.5 is a double literal; 0.5f is a float literal.
TUTORIAL BEHAVIOR

rotationSpeed is degrees per rendered frame. This matches the supplied tutorial and makes 0.5 a useful test value.

TIME-BASED BEHAVIOR

rotationSpeed * Time.deltaTime interprets the field as degrees per second and is stable across different frame rates.

Three-value test Test Rotation Speed at 0, 0.25, and 1 without changing any other field. Describe the observable difference, then keep a value that is readable while the player approaches.

05 · COLLIDER → TRIGGER EVENT

Detect overlap without creating a physical barrier

A physical collider blocks or deflects the Player. A trigger collider keeps the overlap volume but removes the solid response, allowing OnTriggerEnter to report that the Player entered it.

  1. Place the collectible directly in Player’s path, enter Play mode, and collide with it while its Collider is still physical.
  2. Exit Play mode, select the collectible, locate its Collider component, and enable Is Trigger.
  3. Test again. Player should pass through without resistance, but the collectible should remain visible.
  4. Open Collectible.cs and add OnTriggerEnter(Collider other) after Update but before the class’s final brace.
  5. Plan the behavior with the comment // Destroy the collectible.
  6. Add Destroy(gameObject);, save, and retest. The collectible should disappear from both the Scene and Hierarchy when entered.
PHYSICAL COLLIDER

Produces contact response. The Player bumps into the collectible, which is wrong for a pickup.

TRIGGER COLLIDER

Reports overlap without blocking. It supplies the event needed for a pickup.

Physics requirement Trigger interaction requires Colliders on the participating objects and at least one Rigidbody or ArticulationBody in the interaction. The supplied Player prefab already has a Rigidbody.
Controlled before / after Preserve two observations: before Is Trigger, Player is blocked; after Is Trigger but before Destroy, Player passes through and the collectible remains. This separates physics configuration from scripted response.
Change a Collider into a triggerCompare blocking contact with non-blocking overlap
06 · EVENT → CONDITION → FEEDBACK

Spawn feedback and restrict collection to Player

The initial trigger destroys the collectible for any qualifying physics object. The completed event adds two responsibilities: instantiate a VFX prefab at the pickup position, and run the pickup actions only when the entering Collider carries the Player tag.

  1. In _Unity Essentials → Prefabs → VFX, preview the non-2D particle prefabs and choose one. Exit Prefab editing mode with the Hierarchy back arrow.
  2. Declare public GameObject onCollectEffect; below rotationSpeed, save, and return to Unity.
  3. Drag the selected VFX prefab onto On Collect Effect in the collectible’s Inspector.
  4. Inside OnTriggerEnter, add Instantiate(onCollectEffect, transform.position, transform.rotation);.
  5. Select Player and choose Player from the Inspector’s Tag dropdown.
  6. Add if (other.CompareTag("Player")) and move both pickup actions inside its braces.
  7. Save, test a Player pickup, then test a collectible overlapping a chair or couch. Furniture must not collect it.
StageQuestion answeredObservable result
Trigger overlapDid a physics object enter this volume?OnTriggerEnter receives the other Collider.
Tag conditionIs that other object the Player?Furniture is ignored; Player continues.
InstantiateWhat feedback appears, and where?A VFX prefab is copied at the collectible Transform.
DestroyWhat object leaves the scene?The collectible is removed after the current update loop.
Why the final two lines work Destroy(gameObject) schedules destruction after the current update loop; it does not erase the Transform in the middle of this method. The following Instantiate call can still read the collectible’s position and rotation.
Required references and exact labels Assign On Collect Effect before testing, and use the exact tag Player. A missing prefab reference or a tag/capitalization mismatch prevents the intended result and should produce a Console error or a failed condition.
Positive and negative evidence Prove both branches: Player collects one item and creates VFX; a chair or couch overlapping a second item does not collect it. A positive pickup alone does not prove the tag filter.
Instantiate pickup VFXAssign the prefab reference and spawn it at the collectible Restrict collection to PlayerAdd the tag and move pickup actions inside the condition

07 · DUPLICATE → SNAP → ORGANIZE

Turn one working pickup into a readable route

Configure and test one correct collectible before duplicating it. The duplicates inherit the attached script and serialized field values; placement and hierarchy organization then become scene-design responsibilities.

  1. Switch the Scene view handle orientation to Global, frame 03_Living_Room, and use the Scene gizmo to select Top view.
  2. Select the Move tool and the working collectible.
  3. Press Ctrl+D (macOS: Cmd+D) to duplicate it.
  4. Move the duplicate along one world axis while holding Ctrl (macOS: Cmd) to snap at fixed increments.
  5. Repeat duplicate-then-move to create a route that takes Player through more than one part of the room.
  6. Shift-select the collectible instances in the Hierarchy, right-click, and select Create Empty Parent.
  7. Rename the new parent Collectibles. Use F2 (macOS: Return) for quick renaming.
LOCAL FOR ROTATION

Use Local orientation to reason about the collectible’s own Y-axis while planning its spin.

GLOBAL FOR PLACEMENT

Use Global orientation to align duplicates along world axes regardless of each object’s rotation.

Route quality test Start at the entrance and collect the route without reversing into walls or losing sight of the next item. If the next target is unclear, reposition only the route; do not change movement code to compensate for poor placement.
